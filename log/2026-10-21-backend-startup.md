# 后端启动性能调优记录

记录日期为 2026-10-21。涉及 TUI 首次挂载、模型能力查询接口和桌面端能力展示。

基线版本为 `27529a0904896d883d9c92137a380c64eec3f246`，修复代码版本为 `f39e834715facdf50ec8efe143d0d7fc190e4e42`。测量脚本、原始数据和完整报告随 `7f5b6fc` 提交。

## 现象

从输入 TUI 启动命令到能够输入文字，用户需要等待较长时间。三次基线测量分别为 15.253、8.314、20.176 秒，中位数为 15.253 秒。

桌面后端的首次 `GET /api/config/llm/capabilities` 同样出现长等待，三次测量分别为 70.774、5.438、71.634 秒。同一进程再次查询降至毫秒级。源码服务的 `/health` 中位数为 2.217 秒，因此能力接口延迟不能直接视为整个桌面程序的启动时间。

## 原因与证据

TUI 的 `ChatScreen.on_mount()` 同步刷新模型面板。面板读取 `AgentLLM.capabilities`，这个属性在缺少明确能力配置时同步发起远程探测。探测先确认工具调用，再确认并行工具调用或 JSON mode，每条路径最多请求两次。

远程探测在 Textual 主线程上执行，阻塞挂载和输入处理。三次探测分别耗时 12.993、5.966、17.995 秒，占启动耗时的 72% 至 89%。同期 `AppRuntime.build()` 中位数仅为 1.029 秒。主要等待来自挂载期间的远程 I/O。

实现还存在以下问题：

- HTTP 能力接口读取同一属性，也会等待探测。
- 缓存只存在于进程内，重启后重新探测。旧缓存标识未隔离凭证。
- 全局锁覆盖远程请求，不同模型的探测会互相等待。
- 探测复用普通聊天的超时与重试策略，没有独立的短总预算。
- 面板为显示上下文窗口而触发工具和 JSON 能力探测，但这些请求不能补出缺失的上下文窗口大小。

## 修复方式

| 提交 | 修复 |
| --- | --- |
| `64efd00` | 将能力读取和远程探测分开。展示只读本地快照，真实任务通过显式操作确认未知协议。 |
| `30c1eb9` | 成功结果持久化 24 小时，同一配置合并探测，不同模型允许并行。缓存摘要包含模型、端点、凭证和能力配置。失败保持未知并在进程内退避 30 秒。 |
| `58f0473` | TUI 首次绘制后后台探测。桌面端通过 POST 发起探测并轮询 GET，明确展示未知、探测中、成功与失败状态。 |
| `f39e834` | 两次探测共享最多 5 秒的网络预算，关闭探测连接和 SDK 自动重试。保护模型切换与快照读取，避免旧配置覆盖新模型。 |
| `7f5b6fc` | 提交可重复运行的启动测量脚本、原始样本及报告。 |

普通聊天继续使用原有连接池与超时配置。记忆、RAG、MCP、技能和 embedding 预热均保留，未通过强制修改能力布尔配置绕过探测。

## 结果与测量口径

环境为 Windows 11、Python 3.13.6、16 个逻辑处理器。使用同一现有配置和数据库内容，基线每组 3 次，修复后每组 10 次，串行运行全新进程。每个样本使用临时配置与 SQLite 在线备份，修复后不复用能力缓存。

从父进程创建子进程前开始计时。TUI 运行真实 CLI、runtime 和 Textual headless driver，直到输入框接受 `Key('x', 'x')` 并显示字符才算可输入，不等待 CPU 空闲。HTTP 测量启动真实服务，以 25 毫秒间隔轮询 `/health`。操作系统和模型文件缓存保留。

下表为中位数：

| 指标 | 修复前 | 修复后 | 修复后范围 |
| --- | ---: | ---: | ---: |
| TUI 进程创建到按键回显 | 15.253 秒 | 2.390 秒 | 2.294 至 2.798 秒 |
| TUI 内部 runtime 构建 | 1.029 秒 | 1.135 秒 | 见原始事件 |
| 后端进程创建到 `/health` 200 | 2.217 秒 | 2.167 秒 | 2.033 至 2.601 秒 |
| 首次 GET 能力接口 | 70.774 秒 | 5.968 毫秒 | 3.230 至 36.556 毫秒 |
| 再次 GET 能力接口 | 15.749 毫秒 | 18.356 毫秒 | 3.201 至 67.929 毫秒 |
| POST 能力刷新接口 | 无此接口 | 10.043 毫秒 | 3.461 至 27.834 毫秒 |

TUI 可输入耗时中位数减少 84.3%，修复后十次均低于 3 秒。健康检查耗时基本不变，收益来自消除界面挂载和首次能力查询中的网络等待。

修复后每次首次 GET 均返回未知状态，POST 返回探测中状态。展示请求完成时无需等待远程探测，成功后的能力更新由真实 HTTP 集成测试验证。

## 验证与限制

相关 Python 回归集合 350 项通过。加严超时测试，要求服务端确实收到请求后，完整启动集成文件再次验证，16 项通过。桌面完整 vitest 为 42 个文件、237 项通过。TypeScript、改动文件的 ruff、无注释门禁和 `git diff --check` 均通过。

覆盖慢端点下的 TUI 输入、只读查询零网络调用、异步刷新、任务工具协议、跨进程缓存、凭证隔离、缓存损坏、并发合并、模型切换竞争、共享截止期限以及超时后的连接和线程回收。

这些结果不包含真实终端绘制、Electron 首帧或历史会话恢复。已安装的桌面程序尚未重新构建。测量属于冷进程、热文件缓存，样本量不足以报告 P95 或 P99。
